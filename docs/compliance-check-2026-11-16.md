# コンプライアンスチェックの記録（2026-11-16）

2026-11-16、開発者自身でコンプライアンスチェックを行った。外部の第三者による監査ではなく、指摘の洗い出しに生成 AI の出力も使ったセルフチェックである。対象はコミット `4c5ebbe` 時点のコードとドキュメントで、指摘は12項目（サーバーの待ち受けと認証、記事本文の保存と表示、取得方法と各媒体の規約、RSS 抜粋と社説の扱い、ウォッチ語や閲覧記録の保存、画像の参照方法、SSRF 対策と応答サイズ、同梱ライブラリのライセンス表示、ビルド時の Node 取得方法、保存データへの訂正・削除の申出経路、広告・ステマ規制、生成 AI の有無と表示ラベルの区別）。

この文書はチェックの指摘全文の転載ではなく、項目ごとの棚卸し結果と、その結果として決めたことの記録。要件としての決定は REQUIREMENTS.md にも同日付で記録した。

## 棚卸しの結果

チェックの前提には「共有・ホスティング型のサービスとして運用される」場合の論点が含まれていた。一行ニュースは個人が自分の端末で動かすリーダーで、その前提に当たらない項目は「記録のみ」とした。ただし前提の食い違い自体が実装と合っていない項目（既定の待ち受け範囲など）は、言い訳にせず直す側に倒した。

対応すると決めたもの:

- サーバーの既定の待ち受けをループバック（127.0.0.1）に絞る。LAN に出す場合はトークン設定を前提にする（指摘 #1 の中核）
- 同梱する第三者ライブラリ（React 等）のライセンス表示を exe とリポジトリに含める（#8）
- ビルド時に取得する Node 実行ファイルのチェックサム照合を行う（#9。コード署名は従来どおり見送り）
- サービスワーカーのキャッシュ範囲を同一オリジンの静的ファイルに限る（#6）
- キーワードウォッチの語が Google ニュース検索に送られる旨を、設定画面に注記する（#5）
- 外部応答の読み取りにサイズ上限を設ける（#7 のうちサイズ上限のみ）
- README のスクリーンショットは、記事の見出し・抜粋・写真が判読できないよう加工する（#4。加工済みの画像で差し替え済み）

記録のみとしたもの（共有・ホスティング型の運用を始めることがあれば再検討する）:

- ウォッチ語や記者名などの保存に関する、事業者としての個人情報保護法上の整理（#5 の残り。個人利用の範囲では現状の保存で足りると判断）
- SSRF 対策の DNS リバインディング対策（#7 の残り）
- 配信元の訂正・削除に追随する仕組みと、権利者からの申出専用窓口（#10。現状は X と GitHub Issues が窓口）
- 広告・アフィリエイトを入れる場合のステマ規制対応（#11。現状は広告なし、収益経路は Ko-fi の寄付のみ）

## 本文機能の廃止

棚卸しと並行して、本文まわりは個別対応ではなく機能ごとやめることにした。判断は2層に分かれる。

設計判断として、記事ページの自動取得をやめる。本文の取得・保存・表示、本文からの「要点」抽出、Google ニュースのラッパー URL の非公式な解決（batchexecute 経路）を廃止した。取得する外部リソースは RSS フィードだけになった。

製品判断として、画像表示、記者名の表示と記者ビュー、本文を対象にした検索・キーワードウォッチの照合も、今回の見直しで終了した。あわせて「本文あり」を優遇する並び替え・スコアブーストと、本文の再整形などの本文専用処理も撤去した。

画像については経緯を正確に書いておく。チェック対象コミットでは、画像は記事ページの og:image だけでなく、RSS のサムネイル／添付画像（media:thumbnail、media:content、enclosure、description 内の img）からも取得する処理があった。したがって画像表示の終了は、本文取得を止めた結果として技術的に避けられなかったものではない。RSS 由来に限る案も検討したが、現行の配信では RSS 由来の画像は実測でほぼ取得できていなかった（実 DB の記事 3,464 件で画像 URL を持つのは 96 件、全て og:image 由来で、RSS 由来は 0 件）。残しても画面にほぼ出ない機能のために取得と表示の説明範囲を広げ続ける理由が薄く、画像表示自体を終了する選択をした。

理由はユーザーの言葉で残す。「堂々とやってることを説明できないなら機能が充実してても意味ない」「ニュースポータル的な使い勝手が落としどころ」。

## 判断の軸

一行ニュースは、公開 RSS を集め、同じニュースを各媒体がどう報じているかを見比べ、元記事へ移動するための個人用リーダーとする。取得する情報とその使い方を利用者や配信元に具体的に説明できることを、機能を増やすことより優先した。

公開 RSS の取得頻度、利用条件、抜粋の表示範囲は、引き続き配信元ごとに確認する。

## 対応の実施

棚卸しで「対応する」とした残件は、同日中にすべて実施した。

- 待ち受け: サーバーの既定を `127.0.0.1` にした。別端末から開く場合は `HOST` の明示指定が必要で、その場合は `ACCESS_TOKEN` の設定を前提とするよう README の案内もそろえた（#1）
- 第三者ライセンス: 配布物に含まれる React・React DOM・scheduler と、exe の土台の Node.js のライセンス文を `third-party-licenses.txt` にまとめ、Web 配布と exe の両方に同梱した。生成は `scripts/generate-licenses.mjs` で行う（#8）
- ビルド時の Node 取得: バージョンを v24.22.3 に固定し（`scripts/build-sea.mjs` の `NODE_VERSION`）、ダウンロードした node.exe を公式 SHASUMS256.txt と照合してから使うようにした。キャッシュ済みのファイルもビルドのたびに照合する（#9）
- サービスワーカー: キャッシュ対象を同一オリジンの静的ファイルだけに限り、キャッシュ名を上げて旧キャッシュ（外部オリジンの応答を含み得るもの）を破棄させた（#6）
- キーワードウォッチの注記: 設定画面のキーワード管理に「登録したキーワードは、収集のために更新のたび Google ニュース検索に送信されます」と明記した。README の設定の節にも同じ注記を入れた（#5）
- 応答サイズ上限: RSS など外部応答の読み取りに 5MB の上限を設け、上限を超えたらそのフィードの取得を失敗として扱う。API が受け取る JSON にも 64KB の上限を設けた（#7 のうちサイズ上限）

## 移行

既存の DB に保存済みの本文・画像 URL・記者名・本文由来の抽出文は、起動時と更新時の処理で自動的に消去する（冪等。検索用テキストはタイトルと要約だけで作り直す）。VM 上の実 DB のコピーで検証し、旧データを持つ 235 記事分が消去され、再実行では 0 件だった。利用者の実機でも、次回起動・更新で同じ消去が走る。

## 2回目のチェック（2026-11-16）

同日、対応後の状態に対して2回目のチェックを行った。対象は GitHub の main（`c9d461d`）と公開リリース v0.2.0（`b4fa54c`）。前回の最優先2件（既定での LAN 露出、記事本文の取得・配信）は解消を確認した。他の実施済み項目（スクリーンショットの加工と経緯の記録、ウォッチ語の注記、サービスワーカーのキャッシュ範囲、応答サイズ上限、第三者ライセンスの同梱、ビルド時の Node チェックサム照合）も対応を確認した。残った指摘は次の4件で、対応もあわせて記録する。

対応したもの:

- 社説 RSS のタイムアウト（中）: 社説取得は fetch() の直後にタイマーを解除してから本文を読んでいたため、応答が途中で止まると待ち続ける余地があった。通常フィードと取得処理を共用し（`fetchRssText`）、本文の読み取り完了までタイマーを残す形に統一した
- LAN 利用時のトークン（中・LAN 利用時のみ）: README はトークンを前提と案内していたが、サーバー側は必須にしていなかった。ループバック（`127.0.0.1` / `::1` / `localhost`）以外で待ち受ける設定で `ACCESS_TOKEN` が空の場合、起動時にエラーを出して終了するようにした。README の案内も実態にそろえた
- 公開文面のずれ（低）: 画面の「要点」ラベルと README の「仕組み」節が、廃止した旧抽出方式（数字や固有名詞を優先して最大3文を選ぶ）の説明のままだった。ラベルを「RSS 抜粋」に変更し、説明を現行の実態（RSS で届いた抜粋を、文の切れ目を保って先頭から一定の長さに整形して表示する）に書き換えた
- Windows 上で作る exe の Node（低・配布ビルド時）: Windows ネイティブビルドでは実行マシンの Node（`process.execPath`）を土台にするため、固定版 v24.22.3 のダウンロード・照合が効かず、同梱ライセンスの Node 表記とずれる余地があった。ネイティブビルドでも `process.version` が固定版と一致するか照合し、違えば必要なバージョンを表示して中止するようにした

記録のみとしたもの:

- リリースノートの「コンプライアンス的に NG」の表現: チェックでは「記録文書が示す判断より断定的」と指摘されたが、開発者の判断で現行表記のまま維持する
- モザイク加工前のスクリーンショットは、旧コミットの履歴から引き続き閲覧できる。git の性質として受容する（履歴の書き換えはしない）
- RSS の利用条件: 公開 RSS が対象で取得時に User-Agent を送っているが、媒体別の robots 判定や 429 時の待機までは確認できていない。配信元ごとに取得頻度と見出し・抜粋の表示条件を確認する、という従来の軸のまま残る論点とする
